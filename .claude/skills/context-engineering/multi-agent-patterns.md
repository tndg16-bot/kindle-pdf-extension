# Multi-Agent Architecture Patterns

## When to Activate
- 単一エージェントのコンテキスト制限がタスク複雑性を制約する時
- タスクが自然に並列サブタスクに分解される時
- 異なるサブタスクが異なるツールセットやシステムプロンプトを必要とする時
- 複数ドメインを同時に処理するシステム構築時
- 単一コンテキスト限界を超えてエージェント能力をスケールする時

## Core Concepts

### なぜマルチエージェントか
マルチエージェントシステムは、分散によって単一エージェントのコンテキスト制限に対処する。
**重要な設計原則**: サブエージェントは「組織的役割のシミュレーション」ではなく、
「コンテキスト分割」のために存在する。

### 3つの主要パターン

#### 1. Supervisor/Orchestrator（監督者パターン）
```
        [Orchestrator]
         /    |    \
     [Agent] [Agent] [Agent]
```
- **中央集権制御**: オーケストレーターがタスク分配と結果統合を担当
- **利点**: 明確な責任分離、デバッグが容易
- **欠点**: ボトルネックになりやすい

#### 2. Peer-to-peer/Swarm（スウォームパターン）
```
    [Agent] ⇔ [Agent]
       ⇕         ⇕
    [Agent] ⇔ [Agent]
```
- **柔軟なハンドオフ**: エージェント間で直接タスクを渡し合う
- **利点**: スケーラブル、耐障害性
- **欠点**: 調整が複雑

#### 3. Hierarchical（階層パターン）
```
        [Manager]
         /    \
    [Lead]    [Lead]
     / \       / \
  [A] [A]   [A] [A]
```
- **階層的抽象化**: 各レイヤーが異なる抽象度で動作
- **利点**: 複雑なタスクの分解に適する
- **欠点**: レイテンシ増加

## Context Isolation（コンテキスト分離）

**最重要設計原則**: 各サブエージェントは独立したコンテキストを持つ

### 分離のメリット
1. **専門化**: 各エージェントが専門領域に集中
2. **並列実行**: 独立したコンテキストで同時実行可能
3. **デバッグ容易性**: 問題を特定のエージェントに限定
4. **スケーラビリティ**: エージェント追加が容易

### 調整プロトコル
- **明示的なハンドオフ**: タスク受け渡し時に必要情報を明記
- **構造化された出力**: JSONスキーマなどで結果を標準化
- **エラー伝播の制御**: 失敗を適切にエスカレーション

## Failure Modes and Mitigations

| 障害モード | 説明 | 対策 |
|-----------|------|------|
| Bottleneck | オーケストレーターが過負荷 | 非同期処理、タスクキュー |
| Divergence | エージェント間で結果が矛盾 | コンセンサスメカニズム |
| Error Propagation | 1つの失敗が連鎖 | サーキットブレーカー |
| Sycophancy | 過度の同意（独立判断の欠如） | 独立評価の確保 |
